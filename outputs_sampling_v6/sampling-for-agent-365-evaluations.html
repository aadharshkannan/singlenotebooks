Sampling for Agent 365 Evaluations

Evaluate every agent without sending every session to an LLM judge.

SAMPLING RESEARCH · V4 + V6
Speaker notes. Agent 365 provides an enterprise control plane for observing, governing, and securing agents. Evaluation turns that observability into an answer to a business question: are agents completing work successfully and behaving as intended? The challenge is scale. We want evaluation coverage across every agent and every session, but LLM judges have real cost and capacity constraints. This presentation explains how sampling controls those constraints, what the experiments taught us, what is implemented today, and the path toward a more intelligent approach.

Cost + available capacity

Sampling turns an unbounded evaluation bill into a controlled capacity decision.
Speaker notes. Our goal is to bring LLM-as-a-Judge evaluation to Agent 365 for all agents. We are starting with Task Completion and expect to expand across seven additional dimensions: Intent Resolution, Task Adherence, Tool Call Accuracy, Tool Call Success, Tool Input Accuracy, Tool Output Utilization, and Tool Selection. Without sampling, each evaluator multiplies the work: one LLM call per session, per evaluator. This creates two constraints before we attach a specific dollar amount: what we can afford and how much LLM throughput is available. Sampling is the control that makes broad evaluation operationally possible.

Speaker notes. Random sampling is the benchmark and simplest production option. It gives every eligible session the same chance. MinHash LSH is a fast way to recognize sessions that use similar words, phrases, and tool patterns. Each session becomes a compact fingerprint. Similar fingerprints land in the same buckets, while a bucket miss signals something less familiar. MinHash does not understand meaning as an embedding model does. Different words can describe the same task, or similar words can describe different tasks. That limitation motivated the semantic approach.

Speaker notes. A full-session embedding converts the whole interaction into a numerical representation of meaning. Similar behavior appears nearby; semantically unusual sessions appear farther away. The embedding selector uses that map to seek broader semantic coverage. This is selection. Inverse Distance Weighting is a separate estimation step. After selected sessions receive observed judge scores, an unjudged session borrows information from nearby judged sessions from the same agent. Closer neighbors receive more weight. The result is a model-assisted estimate, not another LLM judgment.

Speaker notes. The v4 experiment used a labeled population of 2,800 normalized Agent 365-style sessions across 105 agents. Five dense agents contributed 500 sessions each; a broader 100-agent corpus contributed another 300. Each unit contained a structured OpenTelemetry trace, an expected pass/fail outcome, concept metadata, difficulty, and token cost. A concept combined corpus, domain, task, and difficulty, producing 480 distinct concepts. Expected outcomes and concept metadata were not used to select sessions. The population pass rate was 71.18%. The matched token budgets were 65,949; 131,898; 263,797; 395,695; and 659,492 tokens.

Speaker notes. We measured two complementary questions. Selected-only outcome-rate MAE is the absolute gap between the sample pass rate and known full-population pass rate. Smaller is better. Concept coverage is the number of distinct behavior concepts touched by selected sessions divided by the 480 concepts in the population. Higher is better. The metrics can move differently: a sample can estimate the overall rate accurately while missing rare behaviors, or cover broad novelty while distorting the rate. That is why we evaluated both under the same whole-session token budgets.

Speaker notes. Random and MinHash produced similar concept coverage at low budgets. Random led at 5%; MinHash led by less than one point at 10%. From 20% onward, embedding separated. At 30% capacity it covered 78.7% of concepts versus 55.4% for Random. At 50%, it reached 87.9% versus 68.5% for Random and 75.0% for MinHash. On selected-only outcome-rate error, however, Random won four of five cells and MinHash one. The initial IDW-augmented estimate did not beat the simpler selected-only estimate in v4. Random was far simpler to ship and operate, so we implemented it as the immediate control while continuing semantic research. This chart is selection coverage; IDW does not cause the lift.

Speaker notes. The current External3p session-completion path normalizes agent and session identities, hashes them with SHA-256, maps the result to one of 100 buckets, and includes the session when the bucket is below the configured percentage. Each production container has separate memory, and retries can reach another instance. An in-memory cache cannot coordinate that reliably; Redis would add state, network calls, and failure modes. Deterministic hashing lets each container independently recompute the same answer. A per-agent minimum can add sessions, and run or throughput limits can constrain them. This cross-container claim applies to the default SHA-256 session path; the legacy path uses process-seeded HashCode.Combine and does not provide the same guarantee across restarts.

Speaker notes. Random is a strong baseline for estimating an overall rate, but most budget naturally lands where most traffic exists. Semantic selection seeks broader coverage, which matters for rare and unique sessions, especially within super agents that handle many kinds of work. IDW then uses judged sessions as same-agent donors for unjudged sessions. It can assign each eligible session a model-assisted pass probability without pretending it was directly judged. The production contract must retain provenance: judged versus estimated, donors, representation version, and uncertainty. The initial v4 IDW result was mixed, so this remains a validated research direction rather than a production-accuracy claim.

Conditional geometric sensitivity · not a statistical confidence interval
Speaker notes. An IDW estimate does not tell us whether support came from nearly identical sessions or across a sparse region. A Lipschitz bound turns distance into a confidence signal. It assumes expected evaluation scores change smoothly across the semantic map. The allowance is the Lipschitz value multiplied by the weighted average angular distance to judged donors. An estimate of 0.65, weighted angle 0.20, and L of 0.50 gives an allowance of 0.10 and a range of 0.55 to 0.75. This is conditional geometric sensitivity, not a 95% confidence interval. It does not cover evaluator bias, embedding drift, binary outcome noise, or selection bias.

Speaker notes. Native text-embedding-3-small representations contain 1,536 values per session. Embeddings are customer data, so storage must meet corresponding compliance requirements. The initial architecture assumed a vector-capable store. We tested PCA, SVD, Gaussian Random Projection, and a random-coordinate-mean baseline from 1,024 dimensions down to 2. The intended v6 study used 2,500 synthetic sessions from five dense agents, 30 replay seeds, five traffic schedules, and five judge-budget levels, producing 54,750 rows. The reducer was fitted once on the full unlabeled population; replay seeds varied downstream behavior rather than refitting it. We tested the end-to-end result, not merely vector reconstruction.

Speaker notes. Across the intended 30-seed v6 run, PCA at eight dimensions achieved end-to-end MAE 0.2682 versus 0.3476 for native 1,536D: a 0.0794 absolute reduction, about 23%. PCA-8 F1 was 0.8589, a 0.0396 improvement over native. Modeled stored representation was 0.129 MB versus 15.36 MB, about 119 times smaller; this is not total process memory. PCA-8 led this artifact, but the study was synthetic and transductive with one fitted reducer. Selection overlap with native was only 18.9%, so production must validate selected sessions, not only averages. Eight scalar components create a plausible ESP storage path without a dedicated vector index, pending schema, compliance, query, and production performance validation. The experiment did not show a persuasive runtime improvement.
